# Deploying PrestoPass to Render

[`render.yaml`](./render.yaml) is a Blueprint that describes the entire stack. Render
reads it from the repo and creates everything in one pass:

| Service            | Type              | What it runs                                          |
| ------------------ | ----------------- | ----------------------------------------------------- |
| `prestopass-db`    | Postgres 16       | Users, events, seats, confirmed bookings              |
| `prestopass-redis` | Key Value (Redis) | Seat locks, waiting queue, socket pub/sub, task queue |
| `prestopass-api`   | Docker web        | FastAPI + Socket.IO **and** the taskiq payment worker |
| `prestopass-web`   | Node web          | Next.js frontend                                      |

The API and the payment worker share one container. Render's background-worker
type is not available on the free plan, and without a worker running somewhere
every booking stays `PENDING` forever. [`server/docker-entrypoint.sh`](./server/docker-entrypoint.sh)
supervises both processes and takes the container down if either one dies, so a
dead worker restarts instead of silently swallowing the payment queue.

---

## Deploy

**Prerequisites:** a Render account, and this repo pushed to GitHub.

1. **New Blueprint.** In the Render dashboard: **New ▸ Blueprint Instance**, connect
   the `PrestoPass` repo, and let it read `render.yaml`. Render will install its
   GitHub app the first time — this step needs your browser and cannot be scripted.

2. **Leave the optional values blank.** Render prompts for the env vars marked
   `sync: false` (the Razorpay keys, the Google OAuth keys, the seed admin
   credentials). All are optional — skip them. `PAYMENT_PROVIDER` defaults to
   `mock`, which needs no keys and works offline.

3. **Apply.** The first build takes roughly 5–10 minutes. `JWT_SECRET` and
   `SESSION_SECRET` are generated by Render; you never see or set them.
   `alembic upgrade head` runs automatically on every API boot.

4. **Confirm both service URLs.** Two env vars hold each other's public address
   as literals, and they are the most likely first-deploy problem:

   | Service          | Env var              | Must equal                            |
   | ---------------- | -------------------- | ------------------------------------- |
   | `prestopass-api` | `FRONTEND_URL`       | the `prestopass-web` URL              |
   | `prestopass-web` | `NEXT_PUBLIC_API_URL`| the `prestopass-api` URL              |

   If both services kept their names — `https://prestopass-web.onrender.com` and
   `https://prestopass-api.onrender.com` — there is nothing to do. Render appends
   a suffix when a name is already taken globally; if that happened, fix the
   affected value under **Environment** on that service.

   Note the asymmetry when you do change one: `FRONTEND_URL` is read at runtime,
   so the API just restarts. `NEXT_PUBLIC_API_URL` is compiled into the browser
   bundle at **build** time, so `prestopass-web` needs a full redeploy.

   Neither can use `fromService`. `property: host` resolves to Render's private
   network hostname (a bare `prestopass-api`), which is correct for
   service-to-service calls but useless in JavaScript running in a visitor's
   browser — and pointing the two services at each other would be a circular
   reference, which Render rejects outright.

   Symptoms of getting this wrong: pages load fine, but every API call fails —
   CORS errors if `FRONTEND_URL` is wrong, `ERR_NAME_NOT_RESOLVED` or calls to
   `localhost:5000` if `NEXT_PUBLIC_API_URL` is.

5. **Seed sample events** (optional, once). On `prestopass-api ▸ Environment` set
   `SEED_ON_START=1`, and — if you want an admin account — `SEED_ADMIN_EMAIL` and
   `SEED_ADMIN_PASSWORD`. Save, let it redeploy, then set `SEED_ON_START` back to
   `0`. The seed script is idempotent, so a stray extra run is harmless.

   To promote an account you registered through the UI instead, use
   **`prestopass-db` ▸ Connect ▸ PSQL command**:

   ```sql
   UPDATE "User" SET role = 'ADMIN' WHERE email = 'your@email.com';
   ```

## What the free plan actually gives you

Worth knowing before you show this to anyone:

- **Services sleep after ~15 minutes idle.** The first request afterwards takes
  around a minute while the container starts. For a ticketing demo whose whole
  point is real-time behaviour, open the site and let it warm up before showing
  it. Sleeping also stops the payment worker, so a payment left mid-flight
  settles when the service next wakes, not before.
- **Free Postgres is deleted 30 days after creation.** Render will email you.
  Upgrade the instance or recreate it — do not leave real data on it.
- **Free Key Value holds 25 MB and does not persist across restarts.** That is
  fine here: locks, the waiting queue and the seat cache are all rebuildable, and
  the API clears stale queues on startup by design.
- `maxmemoryPolicy` is pinned to `noeviction` in the Blueprint. Do not change it.
  Evicting a seat lock means two people hold the same seat, which is the exact
  failure this project exists to prevent.

Upgrading later: move `prestopass-api` and `prestopass-web` to a paid instance
type, then optionally split the worker onto its own service (below).

## Splitting the worker onto its own service

Once the API is on a paid instance, give the worker its own so a payment backlog
cannot compete with request handling. Add to `render.yaml`:

```yaml
  - type: worker
    name: prestopass-worker
    runtime: docker
    plan: starter
    region: singapore
    rootDir: server
    dockerfilePath: ./Dockerfile
    dockerCommand: /app/docker-entrypoint.sh worker
    envVars:
      # Same DATABASE_URL / REDIS_URL / NODE_ENV / PAYMENT_* values as the API.
      # RUN_MIGRATIONS is deliberately 0: the API owns schema changes, and two
      # services racing `alembic upgrade head` on deploy is asking for trouble.
      - key: RUN_MIGRATIONS
        value: "0"
```

and change the API's command to `/app/docker-entrypoint.sh api` so it stops
starting a worker of its own.

## Switching payments to real Razorpay test mode

`PAYMENT_PROVIDER=mock` is the default and needs nothing. For the real test-mode
checkout (working UPI tab and cards), set on `prestopass-api`:

- `PAYMENT_PROVIDER=razorpay`
- `RAZORPAY_KEY_ID` / `RAZORPAY_KEY_SECRET` — from the Razorpay dashboard, test mode
- `RAZORPAY_WEBHOOK_SECRET` — set in **Settings ▸ Webhooks**, pointing at
  `https://<your-api>.onrender.com/api/payment/webhook`. This is a different
  value from the key secret. Without it the webhook endpoint rejects everything,
  which is the safe default.

Unlike local development, Razorpay can reach your deployed API directly, so the
webhook works without a tunnel.

## Google OAuth (optional)

Set `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, and
`GOOGLE_CALLBACK_URL=https://<your-api>.onrender.com/api/auth/google/callback`,
and add that same callback URL to the Google Cloud console. Sign-in with Google
stays hidden unless both credentials are present.

## Custom domain

Add the domain to `prestopass-web` in Render, then set `FRONTEND_URL` on
`prestopass-api` to it. Keep the old `onrender.com` URL working by putting it in
`FRONTEND_URL_ALT` — both are allowed as CORS origins.

## Troubleshooting

| Symptom                                              | Cause                                                                                                                    |
| ---------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| CORS errors; waiting room never connects             | `FRONTEND_URL` on the API does not match the web service's real URL. Step 4.                                             |
| Frontend calls `localhost:5000` in the browser       | `NEXT_PUBLIC_API_URL` is baked in at **build** time. Changing it needs a redeploy of `prestopass-web`, not a restart.     |
| Bookings stay `PENDING` forever                      | No worker consuming the queue. Check the API logs for `payment worker ready`.                                             |
| `invalid dsn` / unknown connection parameter on boot | A `DATABASE_URL` the driver rejects. `app/config.py` normalises provider URLs to `postgresql+asyncpg://`; check the logs. |
| Everything is slow on the first hit                  | Free-plan cold start. Expected.                                                                                          |

Logs live under each service's **Logs** tab; `prestopass-api` carries both the
API and the worker output, prefixed per process.
